# Risk Orchestrator · контракт ядра

Python 3.12+, стандартная библиотека. Ядро управляет задачами внутри одного процесса и одного цикла asyncio. Единственная точка подачи — await engine.execute(request, worker). Метод возвращает целочисленный результат либо передаёт ошибку вызывающей стороне. Одновременные вызовы представляют независимые заявки. Время подачи определяет присвоенный номер запуска.

## Что взято из анализа конкурентов

| Референс из hak.pdf | Решение для текущего контракта |
|---|---|
| Prefect, стр. 1 и 5 | Допуск по источнику и дате. Читатели совместимы. Запись исключает остальные обращения к тому же срезу. Занятая заявка сохраняется в очереди. |
| Airflow, стр. 1 и 4 | Регламент может обогнать недавно поступившие ручные задачи. Бонус ограничен, чтобы поток регламентов оставлял ручному запуску возможность стартовать. |
| Temporal / Saga, стр. 2 и 6 | Изоляция промежуточного результата. Для одного внутреннего хранилища достаточно проверить и опубликовать пакет изменений один раз. Компенсация потребуется, если исполнитель уже произвёл внешний побочный эффект. |
| Camunda, стр. 2 и 4 | События жизненного цикла с порядковыми номерами. Для ожидания доступны номер блокирующего запуска и конкретный срез. |

## Контракт данных и исполнения

Slice идентифицирует логический ресурс парой (source, day). Значение среза — кортеж целых чисел. Request содержит имя процесса, инициатора, тип запуска и два неизменяемых множества срезов reads и writes. Допускаются срезы за несколько дат. Для обновления по предыдущему значению срез объявляется в обоих множествах. Отсутствующий вход завершает запуск ошибкой. Новый выход может быть создан при публикации.

Исполнитель получает доступный только для чтения снимок заявленных входов. После вычисления возвращает число и словарь со всеми заявленными выходами. До публикации ядро сверяет ключи и проверяет все значения. Между проверкой, записью и завершением запуска нет передачи управления другому исполнителю. Независимые изменения сливаются с текущим состоянием. Исключение или отмена во время вычисления оставляет опубликованные данные прежними.

## Допуск и прогресс

1. Присвоить последовательный номер и зафиксировать QUEUED. По умолчанию допускается суммарно до 256 ожидающих и активных запусков. Переполнение возвращает BufferError до регистрации.
2. Найти конфликт с активным владельцем или с более ранней по рангу несовместимой заявкой. Ранг равен номеру поступления с вычетом пяти для регламента. При равенстве выигрывает меньший номер. Один регламент может обойти до четырёх более ранних ручных заявок. Выполняющаяся работа сохраняет ресурсы.
3. При конфликте записать WAITING и ждать смены состояния конкретного блокирующего запуска. После пробуждения перепроверить весь набор. Это также защищает писателя от непрерывного прихода совместимых между собой читателей. Читатель может пройти раньше конфликтующей заявки, если та ждёт активную задачу на другом срезе. Проверка совместимости со всеми активными задачами обязательна. По умолчанию каждую ожидающую заявку так обходят не более двух читателей. Обходы расходуют лимит только при фактическом допуске и фиксируются в событии RUNNING. Параметр backfill_limit=0 включает прежнюю политику.
4. Допуск проверяется и фиксируется без await. Активный запуск владеет сразу всем объявленным набором. Рёбра ожидания между ожидающими направлены в сторону строго меньшего ранга. Активные задачи больше ничего не запрашивают у диспетчера. При завершающихся исполнителях цикла внутри алгоритма допуска нет.
5. Завершение даёт COMPLETED, FAILED или CANCELLED. Отмена ожидающего запуска также пробуждает его последователей. Журнал хранит последние 2048 событий по умолчанию. Разрыв порядковых номеров означает вытеснение истории. Для полного воспроизведения выбирается достаточный размер журнала.

## Опубликованный снимок

Режим доступен только задачам чтения. При старте ядро копирует ссылки на объявленные входы в неизменяемый снимок, поэтому последующее обновление не меняет расчёт. Захват снимка и публикация пакета происходят без передачи управления циклу событий. Общая версия хранилища увеличивается после каждой успешной публикации. Для многосрезового чтения номер обозначает момент получения согласованного снимка, а не отдельную версию каждого среза. Предыдущие версии остаются в памяти только пока их использует активный расчёт.

События записываются в журнал ядра независимо от доставки подписчику. Ошибка подписчика логируется. При старте ожидавшего владельца связанные заявки проверяют причину повторно, даже если номер блокировщика и срез остались прежними.

## Критерии приёмки

Основной сценарий использует A за 19 и 20 ноября. Пока регламент готовит обновление за 20-е, сумма за 19-е возвращает 9. Ожидающий читатель получает 30 после публикации регламента. Тест удерживает исполнителя событийным барьером.

Другие проверки покрывают совместное чтение, ожидающего писателя, два общих выхода, приоритет и порядок поступления, конкурирующие изменения независимых срезов, исключение, отмену владельца и ожидающего, валидацию, ограничения очереди и журнала. Смешанный сценарий подаёт 160 заявок на восемь срезов и сравнивает каждый ответ и итоговые значения с последовательным пересчётом по порядку завершения.

Запуск из каталога исходников:

    python -B -W error -m unittest -v

## Граница гарантий и следующий слой

Исполнители — зарегистрированные разработчиком асинхронные функции. Они должны завершаться, отдавать управление циклу событий и выполнять вычисления над переданным снимком. Вложенная подача заявки с ожиданием результата внутри владельца ресурса выходит за контракт. Изоляция данных здесь логическая. Python-функция в общем процессе остаётся доверенным кодом. Лимиты очереди и истории ограничивают количество объектов, но размер самих данных требует отдельного бюджета при приёме внешних запросов.

Будущий API должен устанавливать личность и тип запуска на сервере, выбирать обработчик из реестра и ограничивать объём входных данных. Для нескольких процессов потребуется общий арбитр, проверка полномочий владельца при публикации и долговременное состояние. Истечение TTL само по себе оставляет прежнему воркеру возможность поздней записи. Текущий журнал предназначен для диагностики в памяти процесса. Восстановление после его перезапуска, расписание, HTTP и UI относятся к следующим этапам.


## Замеры допуска при конфликте

Команда из корня проекта: `python -B benchmark_conflicts.py`.

Один исполнитель удерживает A около 30 мс. Писатель запрашивает A и B и имитирует работу в течение 10 мс. Читатели запрашивают B и имитируют 6 или 55 мс работы. Скрипт меняет порядок сравниваемых политик между повторами и проверяет конечные данные. В таблице приведены медианы по 15 повторам каждой конфигурации. Среднее ожидание читателей вычисляется внутри каждого прогона.

| Читатели | Ожидание первого, мс | Среднее ожидание, мс | Ожидание писателя, мс | Общее время, мс | Обходы |
|---|---:|---:|---:|---:|---:|
| 2 коротких | 46,94 → 0,04 | 46,96 → 0,03 | 31,27 → 31,34 | 62,69 → 47,11 | 0 → 2 |
| 12 коротких | 46,11 → 0,04 | 46,16 → 39,05 | 30,94 → 31,47 | 62,61 → 63,04 | 0 → 2 |
| 2 длинных | 46,51 → 0,04 | 46,52 → 0,03 | 30,84 → 61,50 | 109,84 → 77,18 | 0 → 2 |

В обоих коротких профилях два допущенных читателя завершились до освобождения A. В длинном профиле писатель дополнительно ждал освобождения B. Лимит ограничивает число обходов, длительность работы определяется исполнителем. Замеры локальные, без HTTP, с синтетическими задержками.
